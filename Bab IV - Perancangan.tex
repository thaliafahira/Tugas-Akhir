\section{Arsitektur Sistem}
Arsitektur sistem aplikasi \textit{tracker} ITB Ultra-Marathon dirancang
menggunakan \textit{layered architecture} yang memisahkan
tanggung jawab setiap komponen sistem secara terstruktur. Arsitektur ini terdiri
dari lima lapisan utama, yaitu \textit{Presentation Layer}, \textit{Application
Layer}, \textit{Business Layer}, \textit{External Services}, dan \textit{Data
Layer}.

Gambar \ref{fig:architecture} menyajikan representasi visual dari arsitektur sistem \textit{tracker} ITB Ultra-Marathon.
\begin{figure}[H]
    \centering
    \captionsetup{justification=centering}
    \includegraphics[width=0.95\textwidth]{images/architecture.png}
    \caption{Arsitektur Sistem Aplikasi \textit{Tracker} ITB Ultra-Marathon}
    \label{fig:architecture}
\end{figure}

\textit{Presentation Layer} terdiri dari dua antarmuka pengguna, yaitu aplikasi
\textit{mobile} berbasis React Native/Expo untuk Peserta, Ketua Tim, Supporter,
dan Penonton, serta aplikasi web berbasis React yang digunakan oleh Panitia untuk
manajemen perlombaan. \textit{Application Layer} berfungsi sebagai pintu masuk seluruh permintaan dari
klien. \textit{API Gateway} menangani \textit{routing}, autentikasi berbasis
\textit{invite link}, dan pembatasan laju permintaan (\textit{rate limiting}).
Di samping itu, PostgREST berperan sebagai lapisan REST API langsung di atas
basis data PostgreSQL untuk operasi baca-tulis yang bersifat standar. \textit{Business Layer} mengandung lima layanan utama. \textit{Race state service}
mengelola status perlombaan, validasi \textit{checkpoint}, dan pergantian \textit{relay}.
\textit{Query service} menangani kebutuhan baca data seperti pemfilteran posisi
pelari dan kalkulasi ETA. \textit{User service} mengelola autentikasi pengguna
melalui mekanisme \textit{invite link} yang menghasilkan \textit{access token}
dan \textit{refresh token}. \textit{Ingestion service} menerima data lokasi GPS
dari perangkat \textit{mobile} melalui HTTP \textit{polling} serta menangani
permintaan darurat (SOS). \textit{Event management service} mengelola konfigurasi
rute, titik \textit{checkpoint}, dan data operasional perlombaan. \textit{External Services} mencakup dua layanan eksternal. Firebase Cloud
Messaging (FCM) digunakan secara eksklusif untuk identifikasi perangkat melalui
FCM token, bukan untuk pengiriman notifikasi \textit{push}. Tile peta
disediakan oleh OpenStreetMap sebagai sumber data kartografi \textit{open-source}. \textit{Data Layer} terdiri dari PostgreSQL sebagai basis data relasional utama,
Redis untuk \textit{caching} dan penyimpanan sesi sementara, serta \textit{object
store} untuk berkas statis seperti data rute GPX.
\section{Pemodelan Fungsional Sistem}
Pemodelan fungsional dari aplikasi \textit{tracker} ITB Ultra-Marathon
direpresentasikan menggunakan \textit{use case diagram} untuk menggambarkan
hubungan antara aktor dengan fungsi-fungsi utama sistem. Diagram ini memberikan
gambaran visual mengenai bagaimana setiap aktor berinteraksi dengan sistem
sesuai dengan kebutuhan dan hak akses masing-masing. Dengan adanya pemodelan
ini, proses identifikasi kebutuhan fungsional dapat dilakukan secara lebih
terstruktur sehingga membantu pengembang dalam memahami alur penggunaan sistem,
cakupan fitur, serta batasan interaksi yang terjadi pada aplikasi yang
dirancang.

Selain digunakan sebagai alat dokumentasi kebutuhan sistem,
\textit{use case diagram} juga membantu dalam proses komunikasi antara
pengembang dan pihak terkait dalam proses pengembangan aplikasi. Melalui
diagram ini, setiap fungsi utama dapat dipetakan secara jelas sehingga
mempermudah proses analisis, perancangan, serta implementasi fitur pada
aplikasi \textit{tracker} ITB Ultra-Marathon.

yang dirancang diharapkan mampu memenuhi kebutuhan pengguna secara menyeluruh selama perlombaan berlangsung.

\subsection{SK-01 Mengirim Lokasi}

Skenario ini menggambarkan proses pengiriman data lokasi GPS oleh Peserta kepada sistem secara berkala selama perlombaan berlangsung. Pada saat Peserta membuka halaman utama aplikasi, sistem secara otomatis memulai siklus pengiriman lokasi dengan interval waktu yang telah ditentukan. Setiap siklus, aplikasi mengirimkan data koordinat, \textit{timestamp}, dan ID peserta ke \textit{backend} melalui \texttt{POST /location}. Apabila pengiriman berhasil, \textit{backend} menyimpan data lokasi ke basis data dan mengembalikan respons \texttt{200 OK}. Apabila pengiriman gagal akibat \textit{timeout} atau gangguan jaringan, data disimpan sementara di \textit{cache} lokal untuk dikirim ulang pada interval berikutnya.

\subsection{SK-02 Melihat ETD, ETA, dan \textit{Activity Metrics}}

Skenario ini menggambarkan proses pengambilan dan penampilan data ETD (\textit{Estimated Time of Departure}), ETA (\textit{Estimated Time of Arrival}), dan metrik aktivitas lari kepada Peserta. Setiap interval \textit{polling}, aplikasi mengirimkan permintaan \texttt{GET /eta-metrics} beserta data lokasi terkini ke \textit{backend}. \textit{Backend} kemudian mengambil data rute dan \textit{checkpoint} dari basis data, menghitung nilai ETA, ETD, serta metrik aktivitas, lalu mengembalikan hasilnya ke aplikasi. Apabila data tersedia, informasi ditampilkan pada antarmuka Peserta. Apabila sinyal GPS terputus, \textit{backend} mengembalikan respons \texttt{204 No Content} dan aplikasi menampilkan status menunggu sinyal GPS.

\subsection{SK-03 Mengirim Notifikasi Darurat}

Skenario ini menggambarkan proses pengiriman sinyal darurat (SOS) oleh Peserta kepada sistem. Peserta membuka halaman utama dan menekan tombol darurat yang tersedia. Setelah tombol ditekan, aplikasi langsung memulai \textit{countdown} sepuluh detik sambil menampilkan opsi pembatalan melalui \textit{double tap}. Apabila Peserta melakukan \textit{double tap} sebelum \textit{countdown} selesai, pengiriman dibatalkan dan \textit{countdown} dihentikan. Apabila \textit{countdown} selesai tanpa pembatalan, aplikasi mengirimkan data lokasi dan ID peserta ke \textit{backend} melalui \texttt{POST /emergency}. \textit{Backend} kemudian menyimpan status darurat peserta ke basis data sebagai tanda bahwa peserta membutuhkan pertolongan.

\subsection{SK-04 Mengubah Visibilitas}

Skenario ini menggambarkan proses pengubahan status visibilitas lokasi oleh Peserta. Peserta mengklik menu \textit{visibility} pada aplikasi, lalu aplikasi mengirimkan permintaan \texttt{PATCH /visibility} ke \textit{backend} untuk memperbarui status lokasi menjadi publik atau privat. \textit{Backend} memperbarui status visibilitas peserta pada basis data dan mengembalikan konfirmasi kepada aplikasi. Apabila pembaruan berhasil, aplikasi menerima respons \texttt{200 OK} beserta status visibilitas terbaru dan menampilkannya pada antarmuka Peserta. Apabila terjadi kesalahan, \textit{backend} mengembalikan kode kesalahan \texttt{400} atau \texttt{500} dan aplikasi menampilkan pesan kesalahan kepada pengguna.

\subsection{SK-05 Melihat \textit{Live Tracking}}

Skenario ini menggambarkan proses pemantauan posisi pelari secara \textit{real-time} oleh aktor yang memiliki akses terhadap data lokasi. Saat aktor membuka halaman utama, aplikasi mengirimkan permintaan awal ke \textit{backend} melalui \texttt{GET /tracking} untuk mengambil posisi pelari terkini. \textit{Backend} mengambil data posisi dari basis data dan mengembalikannya ke aplikasi. Apabila aktor memiliki akses yang valid, baik sebagai pengguna publik maupun pengguna dengan kode tim yang sah, posisi pelari diperbarui secara berkala pada peta melalui mekanisme \textit{polling} atau \textit{WebSocket push}. Apabila akses ditolak karena visibilitas pelari bersifat privat atau kode tim tidak valid, \textit{backend} mengembalikan respons \texttt{403 Forbidden} dan aplikasi menampilkan pesan bahwa data tidak tersedia.

\subsection{SK-06 Membuat Tautan Undangan}

Skenario ini menggambarkan proses pembuatan tautan undangan oleh Panitia atau Ketua Tim untuk mengundang pengguna baru ke dalam sistem. Aktor mengklik menu "undang" pada aplikasi, lalu aplikasi mengirimkan permintaan \texttt{POST /invite-link} ke \textit{backend}. \textit{Backend} membangkitkan kode dan tautan unik, menyimpan kode undangan ke basis data, lalu mengembalikan hasilnya ke aplikasi. Apabila proses berhasil, aplikasi menerima respons \texttt{201 Created} beserta tautan undangan dan secara otomatis menyalinnya ke \textit{clipboard} aktor. Apabila terjadi kesalahan, misalnya karena permintaan tidak valid atau terjadi konflik data, \textit{backend} mengembalikan kode kesalahan \texttt{400} atau \texttt{409} dan aplikasi menampilkan pesan kesalahan.

\subsection{Halaman Spectator}

Halaman Spectator merupakan halaman yang dapat diakses oleh publik maupun penonton yang memiliki kode akses dari pelari. Halaman ini menampilkan posisi pelari yang mengaktifkan visibilitas publik secara \textit{real-time} pada peta interaktif.
